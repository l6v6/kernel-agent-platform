# 第一阶段项目启动与任务分工会议记录

**会议主题：** 中级实训第一阶段——平台基础框架与模拟闭环开发  
**会议日期：** 2026年11月19日  
**参会人员：** 项目组全体成员（组长及 A、B、C、D；具体姓名按实际情况补充）  
**记录人：** 组长  
**会议目标：** 明确第一阶段开发范围、系统架构、模块接口、成员分工、协作方式与阶段性交付要求。

## 一、阶段目标与范围

本阶段优先完成一个可运行、可演示、可测试的最小端到端闭环，不依赖尚未确定或尚未接入的真实大模型 API 和 GPU/NPU 资源。

以 `vector_add`（向量加法）为示例任务，打通以下流程：

1. 用户提交算子任务。
2. backend 创建任务并管理任务状态。
3. Mock Generator 返回预设的示例代码。
4. Mock Executor 返回受控的模拟执行结果，不执行任意生成代码。
5. Correctness Evaluator 比较预期结果与模拟实际结果。
6. Benchmark 模块记录明确标记为模拟数据的性能信息。
7. SQLite 保存任务、代码及结果。
8. 前端展示任务信息、状态、生成代码、正确性结果和模拟性能记录。

**重要边界：** 第一阶段的模拟执行结果和模拟性能数据只用于验证平台流程，不代表真实 GPU/NPU 上的编译、执行或性能表现。

## 二、总体架构与接口约定

项目采用模块化设计，各模块通过事先约定的数据契约协作。先统一输入输出字段和函数签名，再由成员并行开发，最后进行集成。

### 2.1 第一阶段主要模块

- `frontend/`：任务提交、任务列表、任务详情和结果展示。
- `backend/`：任务管理、API、状态管理和工作流编排。
- `agent/`：Mock 算子代码生成。
- `executor/`：受控 Mock 执行，不运行任意生成代码。
- `evaluator/`：正确性评估和模拟性能记录。
- `storage/`：SQLite 数据持久化。
- `tests/`：各模块单元测试、接口测试和集成测试。
- `docs/`：架构、需求、工作流、API、数据契约和分工文档。

### 2.2 数据传递约定

第一阶段 Python 模块之间暂统一使用 Python 字典（`dict`）传递任务数据和结果，不要求当前阶段先定义自定义 `Task` 类。

生成器接口暂定为：

```python
generate(task: dict) -> dict
```

返回值遵循 `docs/data-contracts.md` 中的 `GenerationResult` 字段约定。成功和失败结果使用相同字段结构；`error` 使用包含错误码和错误消息的字典，成功时为 `None`。

生成模块的 Mock 失败测试通过测试代码传入可选字段 `mock_should_fail=True` 触发。该字段仅供 Mock 单元测试使用，不属于正式用户任务 API 字段。

### 2.3 参数校验职责

- backend 在正式 API 入口进行任务字段、类型和业务规则校验。
- 各业务模块仍需进行必要的防御性检查，避免独立调用时因输入缺失或类型错误而出现未处理异常。
- 各模块的成功、失败返回结构应遵循数据契约。

## 三、成员分工

| 成员 | 主要负责内容 | 主要交付物与测试责任 |
|---|---|---|
| 组长 | 总体架构、backend 任务管理与 API、工作流编排、模块集成；同时负责 `evaluator/benchmark.py` 模拟性能记录 | backend 代码、任务状态流转、模拟性能记录、工作流集成测试、最终集成 |
| A | 前端页面及前后端 API 对接 | 任务提交、任务列表/详情/结果展示；API 请求响应与页面交互测试 |
| B | Mock 代码生成模块 | `agent/generator.py`；生成成功、模拟失败、异常输入等单元测试 |
| C | Mock 执行模块 | `executor/runner.py`；模拟执行成功、失败、异常输入等单元测试 |
| D | 正确性评估与 SQLite 持久化 | `evaluator/correctness.py`、`storage/database.py`；正确性评估和数据库读写测试 |

全体成员均需参与接口确认、代码评审、问题反馈和最终端到端联调。测试工作由各模块负责人承担对应模块测试，不集中交给单一成员。

## 四、开发协作流程

1. 先阅读并遵循 `docs/` 中的需求、架构、API、工作流和数据契约。
2. 各成员基于统一的数据契约确认函数输入、输出和错误结构。
3. 在 `dev` 分支基础上创建个人功能分支，例如 `feature/generator`、`feature/executor` 等。
4. 在个人功能分支独立开发和运行单元测试。
5. 完成阶段性交付后推送远程分支，并创建目标为 `dev` 的 Pull Request。
6. 由组长检查接口、测试和代码变更，确认后合并到 `dev`。
7. 模块合并后进行跨模块联调；稳定版本再由组长安排合并到 `main`。
8. 不直接向 `main` 推送功能开发代码；遇到冲突或推送失败时先沟通，不使用强制推送覆盖他人工作。

## 五、阶段性交付要求

各成员可以先提交自己独立完成的模块和单元测试，不必等待其他模块全部完成。第一轮交付以“模块能独立运行、接口符合契约、测试可重复通过”为标准。

- A：前端基础页面及 API 对接/测试结果。
- B：Mock Generator 及成功、失败、异常输入测试。
- C：Mock Executor 及成功、失败、异常输入测试。
- D：正确性评估、SQLite 持久化及对应测试。
- 组长：backend 任务 API、任务状态流转、工作流编排、模拟性能记录和集成测试。

本次会议未指定具体日历截止日期，具体提交时间由组长结合各模块进度另行确认；采用先交可独立测试的模块、再集成的方式推进。

## 六、后续扩展方向

第一阶段先建立稳定接口，不在当前阶段承诺多芯片、多框架的真实兼容性。后续在硬件和软件环境明确后，再逐步接入真实模型 API、真实芯片执行后端和框架适配层。

架构上尽量保持模块接口稳定，使真实生成器、真实执行器和真实性能测量实现能够替换当前 Mock 内部实现；具体适配仍需针对实际芯片、驱动、编译工具链、框架和运行时进行验证。

## 七、会议结论与待办

1. 第一阶段以 `vector_add` 为示例，优先打通 Mock 端到端闭环。
2. Python 版本建议统一为 Python 3.11（建议 3.11.9）；需由组长在团队开发环境中正式确认，并同步到项目 README/环境说明。
3. 第一阶段模块间先使用字典传递数据，按 `docs/data-contracts.md` 约定字段和返回结构。
4. 补充数据契约中 `mock_should_fail` 的测试用途和错误结构约定。
5. 各模块负责人先独立开发和测试，通过 PR 合并到 `dev`。
6. 组长负责跟进接口一致性、集成和阶段性验收。
